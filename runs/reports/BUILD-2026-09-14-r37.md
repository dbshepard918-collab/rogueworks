# BUILD 2026-09-14 (r37) — forge

**Theme: nothing past floor 1 was ever tested, and three crashes were living there.**

`tools.studio.verify_gate` plays `game.main --headless --turns 300`. At 60 Hz that is five seconds of
gameplay, and a run never leaves its starting floor. So every biome after the first, the room
templates the content round generates for them, and every draw call that only happens deeper in the
run were **unreachable by any check**. "Gates green" said nothing about them.

## 1. The gate that made them visible

New `tools/qa/deep_floors.py`: for one floor per biome entry it builds the world, steps 120 ticks,
**renders a frame**, and asserts the world's own invariants. Wired into `tools.selftest` (20 → 21
checks).


It found everything below within minutes of existing.

## 2. P0 — a floor that rolled a secret room crashed the run

`procgen._place_secret_rooms` builds its room dict inline, and that dict had
`id/biome/kind/w/h/x/y/center/props` — **no `spawn_budget`** — while `spawn.populate_floor` reads
`room["spawn_budget"]` for every non-entrance room:

```
KeyError: 'spawn_budget'   (spawn.py:161 -> procgen.py:607)
```

Whether a secret room is placed depends on the layout, so this was a **randomly-triggered run-ending
crash** on any biome, latent since secret rooms were added. Fixed on both sides: the producer now
emits `spawn_budget: 0` (matching content rooms, which all carry 0), and the consumer uses
`room.get("spawn_budget", 0)` — a room template from any source must not be able to end the run.
Verified: floor 11 went from `CRASHED` to `rooms 7, monsters 18`.

## 3. P0 — the HUD crashed on any floor with a secret room

Rendering floor 11 raised `NameError: name 'fs' is not defined` in
`hud._secret_count_indicator`. `fs` is a **local of `draw()`**; the scale lives on the instance as
`self.font_scale`. The indicator only draws when `total > 0`, i.e. when the floor actually has a
secret room — which is why no gate ever hit it. This is also why the gate now **draws**: a step-only
gate cannot see the HUD, and a floor that crashes when rendered looked perfectly healthy.

## 4. P0 — hazard tiles were invisible

`Level` stores the procgen tile sets as `self._burning` / `self._water`, but
`biome_mods.burning_tiles()` / `water_tiles()` looked for `_biome_burning_tiles` /
`_biome_water_tiles`, which **nothing ever set**. Both always returned empty, and their only consumers
are the renderer's tile overlays:

```
renderer.py:263   if (tx, ty) in burning:   name = "floor_burning"
renderer.py:270   if (tx, ty) in water:     name = "floor_water"
```

So burning tiles and water pools were **drawn nowhere** — the player could not see the hazard they
were standing on. Helpers now read whichever attribute exists. Measured with `deep_floors`: floor 11
went `pools 0` → `pools 6`, floor 16 `pools 0` → `pools 16`.

## 5. The 4th biome got its modifier (the reason the schema was red)

`biomes.json` declares `modifier: ossuary_toxic` for `sunken_ossuary`; the validator rejected it and
**the code never implemented it** — only `catacombs_darkness`, `ember_heat`, `drowned_water` existed.
That was not schema pedantry: the biome was missing its rule, exactly as the other three have one.

- `biome_mods.py`: `ossuary_toxic` config + `_step_ossuary` + dispatch + state slots/timers. Pools tick
  **poison** (magnitude ramping +1 per 5 floors, like ember heat) and the miasma applies a slow
  stacking `weaken`. It explicitly clears the drowned water penalty — toxic water must not inherit it.
- `procgen.py`: `sunken_ossuary` floors place 3-6 caustic pools (reusing the WATER tile, so the
  renderer already understands it; the *modifier* is what gives the tile its meaning, exactly as
  `drowned_water` does).

Verified it is not vacuous, with a control:

```
  OSSUARY pool -> poison applied: YES at tick 149, statuses=['poison']
  drowned slow wrongly applied:  False  (want False)
  DROWNED control -> slow: True (want True) | poison: False (want False)
```

(First attempt reported "modifier is vacuous". That was my **test** reading `actor.statuses` as a dict
membership check when it is a list of `StatusInstance` objects — a check that reads the wrong
container reports absence for ever. Worth remembering alongside the vacuous-gate lessons.)
