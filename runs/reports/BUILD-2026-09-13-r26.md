## 1. P0.4 — the pixel job, dispatched and landed

Filed as ticket **P0.4** with a measurable acceptance command, then handed to the art bot.

**The defect, measured:** `FONT_GLYPHS` in `game/engine/assets.py` held **45** glyphs
(` !%+-./0-9:A-Z_`) and `BitmapFont.render` falls back to a space for anything else, so 24 printable
ASCII characters rendered as blanks — including `>`, which `draw_list` (menus.py:95) and the
meta-tree cursor (menus.py:131) draw at the selected row. **The menu selection cursor was invisible on
every list.** Real drawn content also lost `&`, `'`, `(`, `)`, `,`, `;`, `=`, `[`, `]`.

To make the job verifiable rather than a matter of opinion I wrote the measuring tool first:
`tools/qa/glyph_coverage.py` scans every string literal that actually reaches a draw call (plus
`game/data/*.json` content values) and requires printable ASCII. Before: exit 1, 24 missing.

**pixel fixed it** — 24 new 3x5 glyphs (`game/engine/assets.py`), `FONT_GLYPHS` now 69 entries, and it
wired the check into `tools.selftest`. Verified by me:

```
$ MSYS_NO_PATHCONV=1 .venv/Scripts/python.exe -m tools.qa.glyph_coverage
glyph coverage: 69 glyph(s) defined, 95 required (printable ASCII), 78 used by drawn strings
OK: every required and in-use character is renderable        (exit 0)
```

**Cursor verification.** The vision audit of the rendered menu said "no visible `>` cursor" — a
10x12-pixel glyph is below what the VLM reliably notices. So I checked the pixels instead of the
opinion. Scanning the gold ink in the selected row of a real `MenuScene` frame:


That column of blobs is exactly the glyph `..#/#.#/.#./#.#/..#` at scale 2. **The cursor is drawn.**
The vision result is recorded here as what it was — a miss — not as the finding.

## 3. The audio pipeline — local, free, and licence-enforced

`tools/audio/gen_music.py` renders game music on the owner's GPU. New venv `.venv-audio`
(torch 2.11.0+cu128 — verified `cuda_available True`, capability `(12, 0)`, RTX 5070 — transformers
5.17, diffusers 0.40, soundfile, scipy). **The game venv never gets torch**; the game still ships on
pygame + stdlib.

### The licence requirement, enforced rather than documented

The owner's requirement: assets ready to ship with no licence paperwork and no account-gated terms.
Every backend therefore declares its weights' licence and gating status, and the tool **refuses to
render** with anything outside the allowlist (`mit`, `apache-2.0`, `cc0-1.0`, `bsd-3-clause`,
`unlicense`) unless `--allow-noncommercial` is passed for a throwaway experiment.

The obvious pick was wrong, and querying the model registry is what caught it:

```
$ curl -s https://huggingface.co/api/models/<repo>   # license + gated, per repo
ACE-Step/acestep-v15-xl-turbo-diffusers  gated=False license=mit
ACE-Step/acestep-v15-xl-sft-diffusers    gated=False license=mit
facebook/musicgen-medium                 gated=False license=cc-by-nc-4.0     <- NON-COMMERCIAL
facebook/audiogen-medium                 gated=False license=cc-by-nc-4.0     <- NON-COMMERCIAL
stabilityai/stable-audio-open-1.0        gated=auto  license=stable-audio-community
```

- **MusicGen is CC-BY-NC-4.0, not MIT.** A MusicGen cue had already been rendered as a probe earlier
  in this round; it was never shipped, and MusicGen's **15 GB of cached weights were deleted** so
  nothing can silently render unshippable audio.
- **`stable-audio-open-1.0` is gated** (`GatedRepoError: 401` on the first fetch) *and* carries a
  bespoke community licence — two independent reasons to keep it out.
- **`ACE-Step/Ace-Step1.5` is not runnable**: the all-in-one repo has no `model_index.json`, so
  `AceStepPipeline.from_pretrained` 404s. The `*-diffusers` conversions are the pipeline repos.

Refusal, verbatim:

```
$ .venv-audio/Scripts/python.exe -m tools.audio.gen_music --backend musicgen --prompt x --out /dev/null
REFUSING to render with backend 'musicgen': licence 'cc-by-nc-4.0' is not in the shipping allowlist
  ['apache-2.0', 'bsd-3-clause', 'cc0-1.0', 'mit', 'unlicense']
Use a shippable backend: ace_step, ace_step_sft                     (exit 2)
```

Policy, provenance and the per-asset ledger: **`docs/AUDIO-LICENSES.md`**.
**Sound effects are not model-generated at all** — they are synthesised procedurally from stdlib
`wave` in `game/engine/audio.py`, so they are wholly owned with zero third-party claim. Every open SFX
model checked (AudioGen, AudioLDM2 class) is CC-BY-NC, so using one would *lower* the licensing
quality of the project.

## 4. Two real bugs found by running it, and fixed

**4a. fp16 produced NaN, and the tool called it a success.** The first ACE-Step render "passed":
`rms 1.0, peak 1.0`. It was garbage. Probing the raw tensor attributed it:

```
audio type: Tensor shape: (1, 2, 240000) dtype: torch.float32
min=nan max=nan mean=nan std=nan
first 20 samples ch0: [nan, nan, ... ]
```

fp16 overflows in this pipeline; writing NaN as PCM-16 clamps every sample to `-1.0`, which yields a
full-scale DC block — loud enough to fool a naive loudness check. Fixed three ways: `--dtype` now
defaults to **bfloat16**, non-finite output is detected **before** anything is written, fp16
auto-retries once in bfloat16, and `describe()` flags `dc_broken`/`invalid` so the tool exits non-zero
instead of reporting a pass.

**4b. A loop "seam" metric that could not see a click.** The first metric compared mean level at head
vs tail (0.247 on a clean render — meaningless). Replaced with the **wrap discontinuity** relative to
the 95th percentile of internal sample-to-sample deltas; a real click is now caught and a clean join
reads ~0.

## 5. It works — the first shippable cue

```
$ .venv-audio/Scripts/python.exe -m tools.audio.gen_music --backend ace_step --steps 8 \
    --seconds 30 --seed 7 --loop-fade 1500 --dtype bfloat16 \
    --prompt "dark fantasy dungeon ambience, slow mournful cello drone, distant dripping cave water
              echoes, sparse and brooding, cinematic game score, instrumental" \
    --out .../amb_catacombs_probe.wav
backend ace_step ... dtype bfloat16
$ .venv-audio/Scripts/python.exe -m tools.audio.gen_music --analyze .../amb_catacombs_probe.wav
  5495444 bytes  44100 Hz  2ch  31.15s
  rms=0.11743 peak=0.89127 dc=0.002076 zcr=0.02306
  loop: wrap=0.000015  click_ratio=0.00 (<= 3.0 is clean) -> CLEAN        (exit 0)
```

MIT-licensed weights, 44.1 kHz stereo, healthy level, no clipping, and a seam 0.001× a normal
sample-to-sample step (i.e. inaudible). Rendered with `license: mit`, `shippable: true` in the JSON
report. The probe lives in `%TEMP%`, not in the repo: shipping it into `assets/audio/` with a manifest
entry is ticket **A-01**, now explicitly open for tempo.

## 10. Incident: `docs/PROGRESS.md` was clobbered, and recovered

While this round was being written up, a sibling cron agent overwrote `docs/PROGRESS.md` with
`write_file`: **515 lines → 20 lines**, destroying the project's whole round history.

Recovery, in order:

1. `git log` — **nothing**. The repo had never been committed, so there was no undo.
2. `hermes checkpoints status` — **0 B**; no snapshot store existed.
3. **Session history.** A `read_file` result containing the complete 515-line log was still in the
   session database (`profiles/forge/state.db`, `messages` rowid 29164, declared `total_lines: 515`).
   The file was rebuilt verbatim from that JSON — line-number prefixes stripped — with the two entries
   written afterwards preserved on top. Verified: 600 lines, 34 round headers, newest and oldest
   entries both present, one duplicate header removed.

Root-cause fixes, both landed in this round:

- **`docs/PROGRESS.md` is append/prepend-only:** read it, then `patch` it. `write_file` on a shared
  log is now a standing prohibition (recorded in `docs/SLAPS.md`-adjacent standards and in forge's
  skill).
- **The repo is committed** (first commit, 631 files) so the next accident is a one-line revert.
  `.gitignore` keeps `tools/art/sd/bin/` (2 GB of vendored CUDA runtimes) out of it.

The lesson is in `roguelite-game-factory` §10 ("Shared documents and recoverability") so no bot repeats it.
