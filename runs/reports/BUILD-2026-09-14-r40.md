# BUILD 2026-09-14 — r40: a malformed acceptance command can no longer punish a bot

Date: 2026-09-14.  Owner: forge.  Lane: `tools/studio/slap.py` (shared review apparatus).

## The defect

SLAP #84 and #85 (both against `forge`, P3) were **unclosable**, and not because the fixes failed.
Their `--fix` values were written as **prose instructions**:

```
#84 fix_command: "Patch docs/PROGRESS.md lines 155-158: change 'P4.7/P4.8 stay open' to ..."
    -> /usr/bin/bash: line 1: 19/19.: No such file or directory        (exit 1)
#85 fix_command: "Edit runs/reports/BUILD-2026-09-14.md line 55 to 'All 7 gates green' ..."
    -> /usr/bin/bash: -c: line 1: unexpected EOF while looking for matching `''   (exit 2)
```

`verify_fix` runs that string through bash, so it can never return 0 — and `close_slap` treats a
non-zero exit as a failed fix, **escalating the offender**: level 1 -> 2 writes the rule into the
bot's `SOUL.md` permanently, level 3 freezes its lane. So the review apparatus was on course to
punish a bot for a broken instrument. Two entries were stuck in exactly that loop.

## What changed

- **`looks_like_command()`** — detects prose passed where a command belongs (first token must be a
  known shell token, an executable path/extension, or a quoted/dotted invocation; leading `VAR=`
  prefixes are stepped over). Case-sensitive on purpose, so `Set ...` is prose and `set ...` is not.
- **`close_slap`** now marks such an entry `MALFORMED ACCEPTANCE COMMAND ... not a bot failure` and
  **applies no escalation** — no level bump, no SOUL rule — and prints the exact reissue command.
- **`--reissue-fix CMD`** (with `--close N`) replaces a bad acceptance command with a real one and
  verifies it; it refuses prose.
- **`--void N --reason "..."`** closes an entry that cannot be verified (artefact gone, superseded)
  with a permanent ledger note, and never escalates.
- **Issue-time warning**: passing a non-command to `--fix` now prints a loud warning that the slap
  will be unverifiable, so the reviewer catches it when writing the slap instead of weeks later.

## Verification

Detector unit-checked against 12 real strings (the two actual bad commands, four prose variants,
and six genuine commands including env-prefixed and quoted-Windows-path forms) — all 12 classified
correctly.

```
$ .venv/Scripts/python.exe -m tools.studio.slap --close 84
  NOT VERIFIABLE: the acceptance command is prose, not a command.
  no escalation applied - fix the instrument, not the bot:
    python -m tools.studio.slap --close 84 --reissue-fix '<real command>'

$ ... --close 85      -> same, exit 0, no escalation
```

Levels confirmed unchanged (`level=1`, `soul_note` empty) for both entries after the close attempt —
proving the escalation path no longer fires on a malformed instrument.

## Resolution of the two stuck slaps

Both were **voided with a recorded reason**, not deleted:

- **#84** — the underlying fix IS landed: `docs/PROGRESS.md` records the stale "stay open"
  contradiction as resolved (line 76). Only the acceptance command was broken.
- **#85** — the target artefact `runs/reports/BUILD-2026-09-14.md` **no longer exists**, so the
  specific defect is moot. The general rule it encoded ("a report's gate count must match the gate
  tool's current list") stays enforced by `verify_gate`.

`--void` requires `--reason`, because a void without a reason is just a deleted record.

## Note for the reviewer

The deeper lesson is the same one this studio keeps re-learning: **an instrument that cannot
succeed is not evidence.** A check that always fails is as useless as one that always passes — it
just does its damage by escalating the innocent. The fix belongs at the instrument, and a bot
should never be punished for a command that was never runnable.
